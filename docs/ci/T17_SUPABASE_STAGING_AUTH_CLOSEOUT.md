## Operational sequencing

The runtime conformance harness requires a **clean checkout**. The Auth-settings and cleanup builders create
Git-safe files inside the checkout. Therefore do not run all three steps sequentially in one dirty working tree.

Preferred procedure:

```text
clean worktree A @ 7cf6371...
    -> real runtime conformance
    -> protected receipt + generated Git-safe PASS index

clean worktree B @ 7cf6371...
    -> protected /config/auth capture
    -> generated Git-safe Auth settings snapshot

owner-authorized provider cleanup
    -> revoke all sessions for the disposable test user
    -> delete the disposable Auth user
    -> protected cleanup attestation
    -> generated Git-safe cleanup evidence

evidence branch from 7cf6371...
    -> bring in the three Git-safe evidence artifacts
    -> run closeout checker
    -> reconcile T17/task/provider docs
    -> regenerate backlog from tasks.json
```

Using two clean worktrees avoids the common failure where generating
`T17_SUPABASE_AUTH_SETTINGS_SNAPSHOT.json` makes the conformance checkout dirty before its commit witness is
recorded.

## Cleanup semantics

"All sessions revoked" means all sessions for the **one disposable conformance test user**, not every user or
session in the Supabase project.

The conformance harness intentionally reports:

```text
provider_cleanup_performed_by_tool: false
```

Do not edit that generated receipt/index to claim otherwise. Provider cleanup is a separate owner-authorized
operation and separate evidence class.

The cleanup record must also preserve these facts:

```text
persistent_princess_binding_created_by_witness: false
application_login_active:                      false
jwt_age_out_required:                          true
project_decommission:                          NOT_APPLICABLE
production_activation:                         false
```

The isolated conformance witness uses `InMemoryIdentityStore`; it does not create a durable Princess account
binding. The retained staging project is not being decommissioned by this closeout. Already-issued access JWTs can
remain cryptographically valid until `exp`, so successful provider cleanup is not described as instantaneous JWT
invalidation.

## Owner-authority boundary

The existing 2026-10-01 account/processor decision remains narrow and must continue to state:


or production approval.

- do not weaken JWT/claim verification to make conformance pass;
- do not delete unrelated provider users/sessions;
- treat provider-schema drift, account drift or runtime failure as a finding and repair/review that condition first.
