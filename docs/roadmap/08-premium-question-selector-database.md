## How T01, T05, T09 and T15 connect

1. T01 publishes product DTO schemas for analysis references, evidence, report projections and Premium packets. It references T26 stable IDs; it does not replace the database.
2. T05 produces actual deterministic facts and regional observations, preserving aggregate feature semantics. Missing evidence is explicit and blocks dependent candidates.
3. T09 assembles the immutable report snapshot. Its source facts, versions and grant scope are the input boundary to Premium.
4. T15 builds deterministic candidate producers only for supported evidence. The database's generator contracts specify legal candidate forms; unsupported generators return an explicit unavailable outcome, not fabricated candidates.
5. T15 selects the applicable frozen question pack and compiles a per-request strict output schema whose enum IDs are limited to that packet. Fixed choices, dynamic choices, cardinality and answer-state behavior remain as defined in source JSON.
6. The provider returns structured picks and bounded text. Application validation resolves every support ID against the packet, checks cardinality and soft-field bounds, rejects new numerical claims, and stores image-only observations outside canonical measurements.
7. T16 evaluates semantic usefulness and safety. Schema validity alone does not make an interpretation correct. Runtime activation and traditional content promotion remain separate gates.

## Implementation contract

Use `selection_domain` and `cardinality` from the [selection contract](../../schema/graphology_interpretation/v1/values/selection_contract.json); do not revive the old roadmap's combined selection-mode enum. Resolve answer states from [answer policy](../../schema/graphology_interpretation/v1/values/answer_states.json), generator rules from [generator contracts](../../schema/graphology_interpretation/v1/candidates/generator_contracts.json), and report placement from [report slots](../../schema/graphology_interpretation/v1/reports/report_slots.json).

Pin database hash, question-pack ID/version, candidate policy version, prompt/output schema version and allowed fact IDs in each Premium packet. Preserve the underlying schema/engine/benchmark/locale manifest. Candidate IDs must be stable within a saved packet, collision-free, owner-scoped and reproducible from the same supported evidence.

Do not send the whole database to the provider. Send the frozen applicable battery, a bounded set of typed facts and eligible candidates, and one authorized handwriting derivative. Text visible inside that image remains untrusted data. No tools, arbitrary retrieval, OCR transcript or model-generated questions in the initial integration.

No-reference is a normal state: reference-based questions and candidates must use their defined unavailable/fallback behavior. Likewise, blocked traditional associations remain blocked even when the database itself is reviewed. Premium can deliver permitted visual/mechanical synthesis without pretending a rule pack is active.

## Tests and change control

Existing checks include compiler freshness, all graphology validators and research-integrity tests. Keep their execution in CI. Add packet-specific tests for unknown IDs, cross-report references, absent generators, empty candidate sets, incompatible versions, excessive selections, refusal, truncation, unsupported claims and consent revocation during generation.

Any change to selectors, questions, mappings, meanings, generator semantics or report slots is a separate versioned content/contract PR with provenance, fixtures, migration policy and review. Neither T01 nor a mobile billing task may reopen T26 as a convenience. Production runtime activation is not a database-status edit.
